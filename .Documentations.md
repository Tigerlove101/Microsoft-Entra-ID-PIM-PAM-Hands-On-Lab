
1. **Lab Objectives**

The primary objectives of this project were to:

* Understand the difference between standard users and privileged users.
* Configure Microsoft Entra Privileged Identity Management.
* Configure eligible rather than permanent administrative access.
* Implement just-in-time privileged access.
* Require MFA when activating privileged roles.
* Require justification for privileged activation.
* Configure approval-based privileged access.
* Implement PIM for cloud-only security groups.
* Demonstrate temporary group membership.
* Configure password writeback for synchronized users.
* Test self-service password reset for an on-premises synchronized user.
* Review PIM audit activity.
* Understand the relationship between on-premises Active Directory and Microsoft Entra ID.
* Apply least-privilege principles to IAM administration.

5. **Password Writeback and Self-Service Password Reset**

One of the initial challenges in the lab involved attempting to reset the password of an on-premises synchronized user from Microsoft Entra.

The initial password-reset attempt failed because the on-premises configuration did not permit the cloud-based password reset operation.

The environment was then configured to support password writeback.

The following functionality was enabled:

* Password writeback for synchronized users
* Password writeback through the configured Microsoft Entra synchronization service
* Self-service password reset
* MFA verification for password reset

The on-premises password policy was also reviewed.

After the configuration was completed, the synchronized user successfully performed a password reset through Microsoft’s password-reset experience.

The resulting workflow was:

User
 |
 | Password reset request
 v
Microsoft Entra
 |
 | MFA verification
 v
Password reset
 |
 | Password writeback
 v
On-Premises Active Directory

This demonstrated how Microsoft Entra can provide cloud-based self-service password reset while maintaining the user’s identity in the on-premises Active Directory environment.



6. **Standard User Access vs Administrative Access**

An important IAM concept demonstrated during the project was the difference between authentication, directory visibility, and authorization.

Simply having a Microsoft Entra account does not automatically provide administrative privileges.

Standard users may have the ability to view certain directory information, while administrative operations require appropriate Microsoft Entra roles.

Examples of Microsoft Entra administrative roles include:

* Directory Readers
* User Administrator
* Global Administrator
* Privileged Role Administrator
* Other specialized administrative roles

The project focused on assigning privileges only when required rather than permanently granting excessive administrative access.

19. IAM/PAM Security Controls Demonstrated

The project demonstrates several major identity-security principles.

Least Privilege

Users receive only the privileges necessary for their role.

Just-In-Time Access

Administrative access is activated only when required.

MFA

Privileged activation requires stronger authentication.

Separation of Duties

Administrative responsibilities can be separated between requesters and approvers.

Temporary Privilege

Privileged access automatically expires.

Auditability

PIM records privileged-access requests and activation activity.

Hybrid Identity

On-premises identity and cloud identity can coexist while maintaining separate administrative boundaries.

23. **Key Lessons Learned**

1. A synchronized user is not automatically an administrator

Synchronization provides identity synchronization; it does not automatically grant administrative privileges.

2. Eligible is different from Active

An eligible user has the ability to request or activate access but does not necessarily hold the privilege continuously.

3. PIM reduces standing privilege

Instead of keeping administrative roles permanently assigned, privileges can be activated only when needed.

4. MFA strengthens privileged access

A password alone should not be sufficient for sensitive administrative activation.

5. Groups can be used as privileged-access boundaries

PIM for Groups allows organizations to control temporary membership in security groups.

6. Hybrid and cloud-only groups have different management considerations

On-premises synchronized groups should generally be managed from their authoritative on-premises source, while cloud-only groups can be managed directly through Microsoft Entra.

7. Audit logs are critical

PIM provides evidence of who requested, activated, and received privileged access.
